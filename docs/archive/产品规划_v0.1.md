**Godot Harbor（godot港）  
产品规划文档 v0.1**

定位：独立于 Godot 编辑器的插件、项目与环境管理中枢  
版本策略：总体覆盖插件管理、项目管理、引擎管理三条主线；采用渐进式实现，首期聚焦插件管理。

# 一、文档摘要

本规划文档用于统一 Godot Harbor 的产品方向、功能边界、阶段范围与实现优先级。产品长期目标覆盖插件管理、项目管理、引擎管理三大方向，但为确保首版交付质量与验证核心价值，MVP 将以“插件管理 + 项目绑定 + 链接应用”作为主线，优先解决插件复用、版本切换和多项目管理混乱问题。

- 长期目标：形成 Godot 开发环境的统一管理入口。
- 近期目标：先把插件作为“全局可复用资产”管理起来。
- 首版核心：中央仓库（Vault）+ 项目绑定（Linker）+ 链接挂载。

# 二、产品背景与核心痛点

Godot 生态中的插件通常直接放在项目的 addons/ 目录内，这种方式简单直接，但在多项目开发、版本测试和环境一致性方面存在明显缺陷。

1.  项目隔离导致重复安装：同一插件在不同项目中需要重复下载、复制和维护。
2.  版本混乱：缺乏中央版本仓库，切换插件版本往往依赖手工覆盖，容易污染项目。
3.  工具割裂：项目、插件和引擎分别由不同路径和方式管理，工作流不连贯。
4.  缺少全局视图：开发者无法直观看到“哪个项目用了哪个插件的哪个版本”。

# 三、产品定位与目标用户

## 3.1 产品定位

Godot Harbor 是一款独立桌面应用，用于为 Godot 开发者提供统一的插件仓库、项目绑定关系管理和环境信息管理能力。它不依赖 Godot 编辑器运行，核心目标是把插件从“项目内部副本”升级为“全局资产”。

## 3.2 目标用户

- 同时维护多个 Godot 项目的独立开发者
- 需要频繁试验不同插件组合的工具开发者与技术美术
- 需要统一项目环境与插件版本的 Godot 小团队负责人

## 3.3 非目标范围

- 首版不覆盖团队云同步与企业级依赖治理
- 首版不承诺兼容所有非标准资产包结构
- 首版不提供插件安全沙箱或代码审计能力

# 四、产品愿景与阶段策略

产品长期范围包含三条主线，但实现上采用渐进式策略，以避免首版功能膨胀。

|     |     |     |     |
| --- | --- | --- | --- |
| 主线  | 长期角色 | 首版状态 | 说明  |
| 插件管理 | 核心主线 | MVP 必做 | 首期重点，验证 Harbor 的核心价值 |
| 项目管理 | 支撑主线 | MVP 必做（基础版） | 用于发现项目、展示状态、承载插件绑定关系 |
| 引擎管理 | 增强主线 | P2+ 渐进实现 | 长期重要，但不作为首版阻塞项 |

阶段原则：规划层面同时提及三大模块，但实施层面坚持“先插件、后项目增强、再引擎管理”的顺序。

# 五、产品目标

## 5.1 MVP 目标

- 让插件只需导入一次，即可被多个项目复用
- 允许用户为单个项目选择某个插件的具体版本
- 通过一键应用，将目标插件挂载到项目 addons/ 中
- 提供冲突检测、权限提示和状态可视化

## 5.2 中长期目标

- 形成 Godot 项目、插件、引擎的统一环境面板
- 实现插件来源追踪、版本切换、更新检测和健康检查
- 为项目快速启动、环境一致性和问题排查提供基础支撑

# 六、核心概念定义

为减少研发歧义，以下概念在整个产品中应保持统一。

1.  Plugin Source（插件来源）：指插件内容的上游来源，如 Git 仓库、Asset Library、本地目录。
2.  Plugin Package（插件包）：指一次导入或下载后落地到 Vault 中的物理内容。
3.  Plugin Unit（插件单元）：指可挂载到某个 Godot 项目 addons/ 下的最小插件单位，通常为一个包含 plugin.cfg 的目录。
4.  Project Binding（项目绑定）：指项目声明启用某个插件某个版本的配置关系。
5.  Mount Strategy（挂载策略）：指插件进入项目目录的方式，如 symlink、junction、copy。

# 七、功能模块设计

## 7.1 插件管理（Vault）—— 首版核心

定位：作为 Harbor 的中央插件仓库，统一承载导入、版本记录、元信息解析和复用关系。

### 核心能力：

- 从 Git URL 导入插件
- 从本地目录导入插件
- 后续支持 Asset Library 下载与导入
- 记录插件版本、来源、兼容性、引用关系
- 展示插件是否被项目绑定、是否可删除

### 首版约束：

- 首版只保证标准 plugin.cfg 插件工作流
- 允许一个导入包中解析出多个 Plugin Unit
- 不以仓库名作为唯一插件标识，内部使用稳定 plugin_id

## 7.2 项目管理（Projects）—— 首版基础支撑

定位：统一发现和展示本地 Godot 项目，为插件绑定与状态预览提供承载面板。

- 支持设置扫描根目录并递归查找 project.godot
- 支持手动添加和拖拽导入项目目录
- 展示项目名称、路径、Godot 版本提示、已链接插件数量、异常状态
- 作为 Linker 左侧选择面板的基础数据来源

说明：项目管理在 MVP 中只做必要能力，不追求复杂的项目工作流功能。

## 7.3 引擎管理（Godot Runtime）—— P2+ 增强模块

定位：为项目提供 Godot 引擎版本登记、选择和启动能力。

- P2 优先支持“手动登记本地引擎路径 + 用指定引擎启动项目”
- 自动下载官方引擎版本可放入后续阶段
- 不作为 MVP 阻塞项，避免拖慢核心主线

# 八、MVP 范围与非范围

## 8.1 MVP 范围

- 插件导入（Git / 本地目录）
- 插件版本记录与基础元信息解析
- 项目扫描与项目卡片展示
- 项目-插件绑定关系配置
- 一键应用链接变更
- 基础冲突检测与错误提示

## 8.2 不在 MVP 范围

- 引擎自动下载与多平台安装细节处理
- 插件更新自动检测
- 团队共享仓库与云同步
- 复杂依赖解析与一键修复全部非标准结构

# 九、核心用户流程

## 9.1 首次使用流程

1.  用户启动 Harbor，设置项目扫描目录。
2.  应用发现本地 Godot 项目并展示项目列表。
3.  用户通过 Git 或本地目录导入一个插件到 Vault。
4.  用户选择某个项目，在 Linker 中勾选目标插件和版本。
5.  用户点击“应用更改”，Harbor 完成差异计算与链接挂载。
6.  用户在 Godot 中打开项目并验证插件生效。

## 9.2 切换插件版本流程

1.  用户选择项目。
2.  用户在插件列表中切换目标版本。
3.  系统展示将删除旧链接并建立新链接的预览。
4.  用户确认应用，系统完成切换并刷新状态。

# 十、关键交互与应用逻辑

## 10.1 Linker 核心布局

- 左侧：项目列表
- 中间：所有可用插件与版本选择
- 右侧：当前项目 addons/ 预览、冲突提示和待应用变更

## 10.2 Apply Changes 后端处理步骤

1.  读取项目当前 addons/ 状态。
2.  读取 Harbor 中保存的目标绑定关系。
3.  计算新增、删除、升级、保持不变的差异。
4.  执行预检查：权限、目标路径冲突、插件源存在性、兼容性提示。
5.  按挂载策略执行变更。
6.  写回项目状态与操作结果。
7.  刷新项目健康状态。

# 十一、文件系统策略与跨平台方案

## 11.1 默认挂载策略

- 优先使用 symlink（符号链接）
- Windows 权限不足时回退到 junction（目录联接）
- 仅在用户明确允许时使用 copy 作为最终降级方案

## 11.2 Apply 前预检查

- 项目路径是否存在且可写
- project.godot 是否存在且可解析
- addons/ 是否存在，不存在则创建
- 目标挂载目录是否已被占用
- 已有目录是否为 Harbor 管理对象
- 插件源目录是否仍存在

## 11.3 Harbor 管理标记

建议在项目 addons/ 下维护一份 Harbor 管理清单，用于标识哪些目录由 Harbor 挂载，避免误删用户自己维护的目录。

# 十二、兼容性与冲突检测

## 12.1 插件识别规则

- 标准规则：目录中存在 plugin.cfg，则视为标准插件候选
- 若一次导入包含多个 plugin.cfg，则解析为多个 Plugin Unit

## 12.2 冲突检测规则

- 两个插件准备挂载到同一 addons 子路径时，阻止应用
- 目标目录已存在且不是 Harbor 管理对象时，阻止应用
- 插件记录存在但物理目录丢失时，阻止应用

## 12.3 兼容性提示规则

- 项目疑似 Godot 4，而插件疑似 Godot 3：高风险警告
- 项目疑似 Godot 3，而插件疑似 Godot 4：高风险警告
- 插件兼容性无法判断：普通警告，不默认阻断

# 十三、数据存储设计

采用本地 JSON 文件存储状态，便于迁移、备份和调试。建议目录结构如下：

~/.godot-harbor/  
settings.json  
projects.json  
plugins.json  
operations.log  
plugins/  
&lt;plugin_id&gt;/  
&lt;version_id&gt;/  
payload/  
engines/

## 13.1 settings.json

- 扫描根目录列表
- 默认挂载策略
- 权限检测缓存
- UI 偏好

## 13.2 plugins.json

- 插件唯一标识 plugin_id
- 显示名称、来源类型、来源地址
- 版本列表及其物理路径
- 解析出的 Plugin Unit 信息
- 兼容性提示与状态

## 13.3 projects.json

- 项目唯一标识、路径和基础信息
- 项目绑定的插件与版本
- 最近一次应用结果
- 项目健康状态

# 十四、异常处理要求

首版必须覆盖主要异常分支，避免只有 happy path。

1.  Git 不可用、拉取失败或网络中断
2.  导入后未检测到有效 plugin.cfg
3.  项目目录不存在或无写权限
4.  Windows 无 symlink 权限
5.  目标路径已被占用
6.  插件源目录被用户手工删除
7.  项目处于只读、占用或部分损坏状态

错误提示原则：必须同时说明“发生了什么”“影响了什么”“用户下一步能做什么”。

# 十五、UI/UX 原则

- 以全局总览为核心，避免把信息埋入多层弹窗
- 把“未应用变更”与“冲突/警告”放在主视图中持续可见
- 项目状态和插件状态应有明显标签：Ready / In Use / Conflict / Warning / Missing Source
- 所有 destructive 操作都应提供二次确认
- 界面交互支持多语言设置

# 十六、技术架构建议

- 桌面框架：Tauri
- 后端：Rust，负责文件系统、链接、Git、解压和路径处理
- 前端：VUE + TailwindCSS，便于快速迭代管理型界面
- 数据持久化：本地 JSON

补充说明：Tauri + Rust 是因为本项目大量涉及本地文件系统操作、跨平台权限处理和路径兼容性，技术选型应优先服务稳定性。

# 十七、路线图（修正版）

|     |     |     |     |
| --- | --- | --- | --- |
| 阶段  | 周期建议 | 目标  | 交付内容 |
| P0 原型验证 | 1~2 周 | 验证核心机制 | Tauri 壳、项目扫描、读取 project.godot、创建/删除链接 |
| P1 MVP 闭环 | 2~3 周 | 先把插件管理做透 | 插件导入、Vault、项目绑定、Apply Changes、JSON 持久化、冲突提示 |
| P2 体验增强 | 2~3 周 | 补足稳定性和可用性 | 权限引导、操作日志、项目健康检查、批量刷新、基础设置页 |
| P3 环境扩展 | 2 周+ | 逐步引入环境能力 | 引擎路径管理、项目快速启动、后续再评估自动下载 |

阶段总原则：规划中保留插件管理、项目管理、引擎管理三大模块，但资源投入和研发节奏必须优先保障插件管理主线先落地。

# 十八、MVP 验收标准

1.  用户可导入一个标准 Godot 插件。
2.  用户可发现并展示至少一个本地项目。
3.  用户可为项目勾选插件并指定版本。
4.  系统可正确创建和移除链接。
5.  重启应用后，插件与项目绑定关系不丢失。
6.  发生冲突或权限不足时，系统给出明确提示。
7.  Windows、macOS、Linux 至少各验证一个基础成功样例。

# 十九、结论

Godot Harbor 的长期价值在于成为 Godot 开发环境的统一管理入口，但其首版成功与否取决于是否先把插件管理做成一个明确、稳定、低心智负担的核心闭环。因此，本规划建议保留“三主线”的长期架构视野，同时在执行层面坚持“先插件管理、再增强项目管理、最后扩展引擎管理”的节奏，以最快速度验证产品价值并降低实现风险。
