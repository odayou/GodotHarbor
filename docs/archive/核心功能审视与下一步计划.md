## 二、实用主义反思

### 核心原则：复杂问题简单化，简单问题高效化

用户举了一个很好的例子：**插件的安装解析其实挺复杂的，那这一块是不是可以把体验闭环迁移到 Godot 引擎本身的相关功能去闭环？**

答案是 **可以，而且应该**。Godot 编辑器本身已经有完善的插件安装/启用/禁用流程。GodotHarbor 不应该重新实现 Godot 已有的能力，而应该做 Godot 不做的事。

### 重新定位：GodotHarbor 应该做什么

| Godot 已经做好的 | GodotHarbor 不需要做 | GodotHarbor 应该做的 |
|-----------------|---------------------|---------------------|
| 插件安装（解压到 addons/） | ❌ 不需要重新实现解压/安装 | ✅ 提供中央仓库和版本管理 |
| 插件启用/禁用 | ❌ 不需要 | ✅ 提供跨项目的插件发现和绑定 |
| plugin.cfg 解析 | ❌ 不需要深度解析 | ✅ 识别插件元数据用于展示 |
| 资源导入缓存 | ❌ 不需要管理 .import | ✅ 确保 addons/ 目录正确挂载 |
| 编辑器内插件配置 | ❌ 不需要 | ✅ 提供版本切换能力 |

### 核心反思结论

**GodotHarbor 的核心价值不是"安装插件"，而是"管理插件的生命周期"**：
1. **发现** — 从哪里获取插件（Asset Library / Git / 本地项目）
2. **集中** — 一个地方存储所有版本
3. **分发** — 将正确版本链接到正确项目
4. **同步** — 版本更新后一键同步到所有项目

### 关于 CLI 的思考

评估报告建议添加 CLI 接口以支持 CI/CD。经分析，**CLI 不是必须的**：

| 维度 | gd-plug / GodotEnv | GodotHarbor |
|------|-------------------|-------------|
| 交互范式 | CLI-first，配置文件是主界面 | GUI-first，配置文件是辅助 |
| CI/CD 方案 | 必须有 CLI（因为没有 GUI） | Copy 模式 + addons/ 提交 git → CI 零配置 |
| 团队协作 | 编辑配置文件 → 运行 CLI | GUI 管理绑定 → 导出 .harbor.yml → 新成员同步 |

**结论**：社区方案需要 CLI 是因为它们没有 GUI，这是它们的局限而非优势。GodotHarbor 的 GUI + .harbor.yml + Copy 模式提交 git 已经覆盖了团队协作和 CI/CD 场景，而且体验更好。

## 三、下一步核心工作目标

按优先级排序，每个目标都遵循"简单、直接"原则：

### 目标1：修复 Copy 模式 bug（P0 - 必须立即修复）✅ 已完成

**问题**：正常 Copy 模式不创建 `.harbor-managed` 标记，导致冲突检测误判。

**方案**：在 `apply_binding` 的 Copy 分支中添加 `.harbor-managed` 标记创建。

**实际完成**：`linker/mod.rs` Copy 分支已创建标记。

### 目标2：将默认挂载策略改为 Copy（P0）✅ 已完成

**问题**：Symlink 默认策略在多项目同时编辑时有写入冲突风险。

**实际完成**：`models/mod.rs` 默认 `MountStrategy::Copy`。

### 目标3：支持 Git 精确版本锁定（P1）✅ 已完成

**问题**：只能 clone 默认分支，无法锁定特定 tag/commit/branch。

**实际完成**：`import_from_git` 支持 `git_ref: Option<&str>`，前端 Git 导入对话框增加 ref 输入框。

### 目标4：项目级声明式配置（P1 — 团队协作的基础）✅ 已完成

**问题**：所有配置存储在 AppData 私有目录，无法纳入版本控制。

**实际完成**：
- 后端：`.harbor.yml` 解析/生成/同步（`harbor_config/mod.rs`）
- 命令：`read_harbor_config`、`write_harbor_config`、`sync_harbor_config`
- 前端：绑定页面"导出配置"和"同步配置"按钮
- 同步结果弹窗展示导入/绑定/跳过/错误详情

### 目标5：UID 冲突预警（P2）✅ 已完成

**问题**：Copy 模式下不同项目可能为同一插件生成不同 UID。

**实际完成**：
- 后端：`scan_uid_list` 扫描 `.uid` 文件，`check_uid_conflicts` 检测冲突
- 前端：绑定插件时自动调用 `check_uid_conflicts`，有冲突弹窗警告，用户可选择"仍然绑定"或取消

### 目标6：简化插件安装流程（P2 — 实用主义核心）✅ 已完成

**问题**：当前导入流程试图完整解析插件结构（plugin.cfg、units 等），对于不含 plugin.cfg 的资产包需要创建"虚拟 Unit"，增加了复杂度。

**实际完成**：
- `parse_plugin_units` 不再强制要求 plugin.cfg（移除 `anyhow::bail!`，返回 `Vec<PluginUnit>` 而非 `Result`）
- `analyze_asset_type` 统一处理：有 plugin.cfg → Plugin，无 → AssetPack（虚拟 Unit）
- `commands/plugin.rs` 的 reference 模式改用 `analyze_asset_type`，不再区分有无 plugin.cfg 的两套逻辑
- 不做"启用插件"——这是 Godot 编辑器的职责

**核心理念**：不强制 plugin.cfg 必须存在，让 GodotHarbor 能管理任何类型的资产（插件、代码模板、资源包、项目模板），而非仅限含 plugin.cfg 的标准插件。
