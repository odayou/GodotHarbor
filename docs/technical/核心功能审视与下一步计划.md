## 一、评估报告问题核查

### 问题1：资源抢占 — ⚠️ 确认存在

| 评估报告说法 | 核查结果 |
|-------------|---------|
| 默认策略为 Symlink | ✅ 确认。`models/mod.rs:366` 默认 `MountStrategy::Symlink` |
| Symlink 写入直达源目录 | ✅ 确认。符号链接本质如此 |
| 无 CoW 机制 | ✅ 确认。代码库中无任何 CoW 实现 |
| 无运行时文件锁 | ✅ 确认。无 flock/lockfile 等机制 |
| Copy 模式安全 | ⚠️ **存在 bug**：正常 Copy 模式不创建 `.harbor-managed` 标记，导致 `is_managed_link` 误判为"非 Harbor 管理" |

**新增发现**：Copy 模式的 `.harbor-managed` 标记只在 `copy_dir_fallback`（Symlink 降级路径）中创建，正常 Copy 模式走的是 `apply_binding` 的另一条路径，遗漏了标记创建。

### 问题2：版本管理 — ⚠️ 确认存在

| 评估报告说法 | 核查结果 |
|-------------|---------|
| 不支持 Git 精确版本锁定 | ✅ 确认。`import_from_git` 仅接受 `git_url`，始终 clone 默认分支 |
| 删除 .git 导致无法增量更新 | ⚠️ 部分准确。`.git` 被备份到 `{version_id}/git/` 但未用于增量更新 |
| 无法锁定 tag/commit/branch | ✅ 确认。`RepoBuilder` 未调用 `.branch()` |

### 问题3：UID 维护 — ⚠️ 确认存在

| 评估报告说法 | 核查结果 |
|-------------|---------|
| 零显式处理 | ⚠️ 部分准确。存在 `godot_resolver/mod.rs` 的 UID 缓存，但仅用于图标解析，不涉及插件 UID 管理 |
| 无 UID 冲突检测 | ✅ 确认 |
| 无升级迁移逻辑 | ✅ 确认 |

**关键洞察**：Symlink 模式下 UID 问题最小化（所有项目共享同一 `.uid` 文件），这恰好是默认策略。但 Copy 模式下存在 UID 重复生成风险。

### 问题4：团队协作 — ⚠️ 确认存在

| 评估报告说法 | 核查结果 |
|-------------|---------|
| 绝对路径 | ✅ 确认。`Project.path` 为绝对路径 |
| 无声明式配置 | ⚠️ 部分准确。存在模板系统（`templates.json`），但不是可提交到 git 的声明式格式 |
| 无 CLI 接口 | ✅ 确认 |
| 无 CI/CD 支持 | ✅ 确认 |

## 二、实用主义反思

### 核心原则：复杂问题简单化，简单问题高效化

用户举了一个很好的例子：**插件的安装解析其实挺复杂的，那这一块是不是可以把体验闭环迁移到 Godot 引擎本身的相关功能去闭环？**

答案是 **可以，而且应该**。Godot 编辑器本身已经有完善的插件安装/启用/禁用流程。GodotHarbor 不应该重新实现 Godot 已有的能力，而应该做 Godot 不做的事。

### 重新定位：GodotHarbor 应该做什么

| Godot 已经做好的 | GodotHarbor 不需要做 | GodotHarbor 应该做的 |
|-----------------|---------------------|---------------------|
| 插件安装（解压到 addons/） | ❌ 不需要重新实现解压/安装 | ✅ 提供中央仓库和版本管理 |
| 插件启用/禁用 | ❌ 不需要 | ✅ 提供跨项目的插件发现和绑定 |
| plugin.cfg 解析 | ❌ 不需要深度解析 | ✅ 识别插件元数据用于展示 |
| 资源导入缓存 | ❌ 不需要管理 .import | ✅ 确保 addons/ 目录正确挂载 |
| 编辑器内插件配置 | ❌ 不需要 | ✅ 提供版本切换能力 |

### 核心反思结论

**GodotHarbor 的核心价值不是"安装插件"，而是"管理插件的生命周期"**：
1. **发现** — 从哪里获取插件（Asset Library / Git / 本地项目）
2. **集中** — 一个地方存储所有版本
3. **分发** — 将正确版本链接到正确项目
4. **同步** — 版本更新后一键同步到所有项目

## 三、下一步核心工作目标

按优先级排序，每个目标都遵循"简单、直接"原则：

### 目标1：修复 Copy 模式 bug（P0 - 必须立即修复）

**问题**：正常 Copy 模式不创建 `.harbor-managed` 标记，导致冲突检测误判。

**方案**：在 `apply_binding` 的 Copy 分支中添加 `.harbor-managed` 标记创建。

**工作量**：1 行代码。

### 目标2：将默认挂载策略改为 Copy（P0）

**问题**：Symlink 默认策略在多项目同时编辑时有写入冲突风险。

**方案**：
- 将 `MountStrategy::Symlink` 默认改为 `MountStrategy::Copy`
- Symlink/Junction 作为高级选项保留
- 在设置页面添加策略说明文案，解释各策略的适用场景

**理由**：存储成本极低（400MB ≈ 0.2元），但 Symlink 的写入冲突风险极高。Copy 是最安全的默认选择。

**工作量**：3 处代码改动 + 文案。

### 目标3：支持 Git 精确版本锁定（P1）

**问题**：只能 clone 默认分支，无法锁定特定 tag/commit/branch。

**方案**：
- `import_from_git` 增加 `git_ref` 可选参数（支持 branch/tag/commit hash）
- 利用已备份的 `.git` 目录做增量更新（`git fetch` + `git checkout`）
- 前端 Git 导入对话框增加 ref 输入框

**工作量**：后端约 50 行改动，前端约 20 行。

### 目标4：项目级声明式配置（P1 — 团队协作的基础）

**问题**：所有配置存储在 AppData 私有目录，无法纳入版本控制。

**方案**：在项目根目录生成 `.harbor.yml`（或 `harbor.json`），内容为：

```yaml
# .harbor.yml — 提交到 git，团队共享
version: 1
bindings:
  - name: my_plugin
    source: https://github.com/user/my_plugin.git
    ref: v2.1.0          # 可选，精确锁定
    mount_path: addons/my_plugin
  - name: shader_pack
    source: asset-library:12345
    mount_path: assets/shader_pack
```

**关键设计**：
- 使用 `name` + `source` 而非 `plugin_id`（UUID 跨机器无意义）
- `source` 支持 git URL、asset-library ID、本地相对路径
- `mount_path` 使用相对路径（相对于项目根目录）
- 提供 `harbor sync` 命令（CLI 或 GUI 按钮）读取 `.harbor.yml` 并自动安装/绑定

**工作量**：约 200 行后端 + 100 行前端。

### 目标5：UID 冲突预警（P2）

**问题**：Copy 模式下不同项目可能为同一插件生成不同 UID。

**方案**：
- 插件导入时，扫描 payload 中所有 `.uid` 文件，记录 UID 清单
- 绑定时，如果目标项目已有同名插件且 UID 不同，弹出警告
- 插件升级时，对比新旧版本的 UID 清单，如有变化提示用户

**简化原则**：不尝试修复 UID 冲突（太复杂），只做检测和预警，让用户决定如何处理。

**工作量**：约 100 行后端 + 50 行前端。

### 目标6：简化插件安装流程（P2 — 实用主义核心）

**问题**：当前导入流程试图完整解析插件结构（plugin.cfg、units 等），对于不含 plugin.cfg 的资产包需要创建"虚拟 Unit"，增加了复杂度。

**方案**：
- **导入时只做最小必要的工作**：下载/复制文件到仓库，记录元数据
- **安装时交给 Godot**：挂载到项目后，Godot 自己会扫描 `addons/` 并识别插件
- **不解析 plugin.cfg 的完整语义**：只读取 name/version/author 用于展示
- **不做"启用插件"**：这是 Godot 编辑器的职责

**理由**：Godot 编辑器在打开项目时会自动扫描 `addons/*/plugin.cfg`，提示用户启用新插件。GodotHarbor 不需要替代这个流程。

**工作量**：主要是简化现有代码，减少约 100 行复杂逻辑。
